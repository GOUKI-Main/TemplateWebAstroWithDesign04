# CLAUDE.md

Astro 7 + Tailwind 4 の静的サイト**テンプレート（デザイン付き）**。Cloudflare
Workers の静的アセットとして配信する。ブログ機能は持たない（固定ページだけの
サイト）。

見た目は最初から入っている「まちのお店」デザイン（元はパン屋のデモサイト
pan-terume）: 生成りの紙の地、手書き風の見出し、縦書きの大見出し、墨線の
装飾イラスト。動き（スクロールの出現・ヘッダーの出し入れ・初回のオープニング）
は yohaku-koumuten の演出を、ライブラリなしで再現したもの。

このファイルは2部構成:

- **第1部 初期セットアップ** — テンプレートから作った直後に、利用者への質問
  だけでサイトを完成させる手順。
- **第2部 設計上の制約** — 触る前に知っておくべきルール。セットアップ中も
  常に守る。

人間向けの導入は `README.md`、機能ごとの削除手順は `FEATURES.md`。

# 第1部 初期セットアップ

## いつ始めるか

会話の最初に `pnpm check:setup` を実行する（`pnpm install` がまだなら先に
実行）。**終了コード 1（未設定項目あり）なら、利用者の依頼内容にかかわらず
「まずサイトの初期設定をしましょう」と提案してから、このフローを始める。**
利用者が「セットアップして」「サイトを作って」と言った場合も同じ。

`TODO(setup): Qn` という目印が、各質問の答えを書き込む場所に置いてある。
`pnpm check:setup` はその残りを一覧するので、完了判定は常にこれで行う。

## 進め方の原則

- **利用者は答えるだけ。** ファイル名・コード・技術用語を利用者に聞かない。
  答えをどのファイルに書くかは下の対応表で決まっている。
- **質問は1ラウンドずつ。** 下の「ラウンド」単位でまとめて聞き、答えを受けて
  から次へ進む。選択式の質問は `AskUserQuestion` ツールを使う（使えない環境
  では番号付きの選択肢を文章で示す）。自由記述は例を添える。
- **文章は Claude が下書きする。** キャッチコピー・説明文・本文・FAQ は、
  利用者から素材（箇条書き・話し言葉で可）をもらい、Claude が整えて見せる。
  「おまかせ」と言われたら、それまでの回答から書いて確認だけ取る。
- **分からない・後で決める、は許す。** その項目は `TODO(setup)` を残したまま
  先へ進み、最後に「未決定の項目」として一覧で伝える。嘘の住所・電話番号・
  実績を作文して埋めない。
- **答えから決まることは聞かない。** 例: 店舗が無いなら住所系は聞かない。
  通販をしないなら特商法表記は聞かない。
- 全ラウンドが終わったら**決定事項の要約を見せて確認**を取ってから書き込む。
  ただし「デザインから」を選んだ場合の配色・書体だけは、ラウンド3の直後に
  書き込んで見た目を確認してもらってよい（下の「始める順番」）。

## 始める順番（ラウンド0）

最初の質問として、`AskUserQuestion` で次を聞く:

> どちらから始めますか？
>
> 1. **デザインから** — 色や雰囲気など、サイトの見た目を先に決める
> 2. **サイトの基本情報から** — サイト名・説明文・連絡先など（検索結果や
>    SNSに出る情報）を先に決める

| 選択                 | ラウンドの順番    |
| -------------------- | ----------------- |
| デザインから         | 3 → 1 → 2 → 4 → 5 |
| サイトの基本情報から | 1 → 2 → 3 → 4 → 5 |

順番が変わるだけで、聞く内容と書き込み先は同じ。どちらでも全ラウンドを通す。
デザインから始めた場合、サイト名が決まるまでは仮の名前のまま見た目を確認して
もらい、文字入りの OG 画像（`og-text`）はサイト名（Q2）が決まってから作る。

### ラウンド3: 見た目

このテンプレートには**デザインが最初から入っている**（「まちのお店」デザイン:
生成りの紙の地・こげ茶の文字・赤と黄の差し色・手書き風の見出し・縦書きの
大見出し・店先のイラスト・スクロールの出現演出。元はパン屋のデモサイト）。
ここで聞くのは「ゼロから作る」ではなく「この見た目をどこまで寄せるか」。

| #   | 質問                                                                                                                                 | 形式                 |
| --- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------- |
| Q9  | 今の雰囲気のままでよいですか？ 色を変えたい場合は、イメージをどう伝えますか？（このまま / 参考サイトのURL / 言葉 / 画像 / おまかせ） | 選択→URL・文章・画像 |
| Q10 | ロゴ画像はありますか？ 掲載したい写真（外観・商品・店内・スタッフ）は？ SNSでシェアされたときの画像に使いたい写真は？                | ファイル提供         |

最初に、トップページのスクリーンショット（広い画面とスマホ幅）を見せてから
聞く（`pnpm build && pnpm preview` を Playwright で撮る）。

**Q9 で「このまま」なら配色は書き換えない。** 変える場合の伝え方は組み合わせてよい:

- **参考サイトのURL** — WebFetch（無ければ `web-fetch` エージェント）で読み、
  配色・背景の明るさ・見出しの雰囲気を拾う。「どこが気に入りましたか？」も聞く。
  読めないサイトはスクリーンショットを送ってもらう。
- **言葉で伝える** — 「もっと落ち着いた」「緑系に」「高級感」、ブランドカラー
  （色コードが分かれば）、好きな色・避けたい色。
- **画像を渡す** — チラシ・名刺・店内写真・ロゴなど。色は `sharp` で実際の値を取る
  （例: `node -e "require('sharp')('<画像>').stats().then(s=>console.log(s.dominant))"`）。
- **おまかせ** — 業種に合わせて差し色（赤・黄）と地の色だけを替えた案を出す。

変える場合は **配色案を2つ** 作り、利用者向けの言葉で見せて選んでもらう:

- 差し替えるのは `@theme` の色トークンの**値だけ**（地 bg / bg-2 / surface /
  card、文字 fg / muted / link、差し色 accent / sun / bread / leaf、罫 border、
  締めの帯 deep）。トークンの名前と数は変えない。
- コントラストを Claude が計算して確認済みのものだけ出す: fg・muted・link は
  bg / bg-2 / surface の上で 4.5:1 以上、on-deep・on-deep-muted は deep の上で
  4.5:1 以上、白（on-deep）は link の上で 4.5:1 以上（ボタンの文字）。accent は
  大きな文字と装飾だけに使うので 3:1 以上でよい。
- 書体は原則そのまま（手書き風の見出しがこのデザインの芯）。「もっとすっきり」
  と言われたら `astro.config.mjs` の `fonts` で見出しの書体を替える案を出す
  （第2部ルール12）。
- 装飾イラスト（`src/assets/images/deco/`）は墨線のイラスト。業種に合わない
  もの（パン・トマトのスタンプ等）は、その `<Image>` を外せばよい。

決まったら書き込み、スクリーンショットで確認を取る。

デザインの決まり:

- 参考サイトは**雰囲気・配色の考え方だけ**を参考にする。ロゴ・文章・写真・
  イラスト・独自の装飾をそのまま写さない。
- 表せるのは第2部のルールの範囲まで: 色はトークンの値の差し替え、動きは
  `src/scripts/motion.ts` の6種類だけ。参考サイトのスライダー・動画背景・
  パララックス等は再現しないことを伝える。
- ダークモードは持たない（イラストが明るい地用の墨線のため。第2部ルール7）。

## 書き込むときの決まり

- **ページの雛形**: 新しいページは既存の `about.astro` をコピーして作る
  （`Base` + `<PageHead>`（題・欧文の添え字・一文）+ `<article class="prose">`
  - 締めの `<CtaBand>` + `canonicalPath`）。`title` はページ名
    だけ（「| サイト名」は自動で付く）、`description` はページごとに書く。
- **写真**: `src/assets/images/` に置き、`astro:assets` の `<Image>` で出す。
  `alt` は必ず内容を説明する文にする（装飾なら `alt=""`）。`public/` に直接
  置かない（最適化されない）。
- **地図の埋め込み**（アクセスページ）: Googleマップの `<iframe>` に
  `loading="lazy"` と `title` を付ける。`public/_headers` の CSP を有効にして
  いる場合は `frame-src https://www.google.com` を足す。
- **配色**: 文字と地のコントラストは 4.5:1 以上（WCAG AA）。組み合わせは
  ラウンド3の一覧のとおり。赤（accent）は大きな文字と装飾だけ。小さな赤文字や
  ボタンの面は link を使う。
- **見本の写真**: `src/assets/images/sample/` はデザイン確認用。利用者の写真が
  無い枠は見本のまま公開しない — 写真が届くまでは未決定の項目として伝える。
- **文章**: 敬体（です・ます）。誇大表現（「No.1」「絶対」など根拠の無いもの）
  は使わない。利用者が言っていない実績・数値・資格を書かない。
- 第2部のルールはセットアップ中も全部守る。

## 構造化データ（JSON-LD）の確定

JSON-LD は `site.ts` から自動で組み立てられるが、**セットアップでは必ず中身を
確かめて確定させる**（画面に出ないので、仮の値のまま公開されても気づけない）。

1. 書き込み後に `pnpm build && pnpm check:jsonld` を実行する。トップページの
   JSON-LD が「検索エンジンに伝える内容」（サイト名・運営者とその種類・ロゴ・
   SNS・店舗の名称/住所/電話/営業時間など）として表示される。
2. その一覧を利用者向けの言葉に直して見せ、「Google にはこの内容で伝わります。
   合っていますか？」と確認を取る。技術用語（`@graph` など）は出さない。
3. 次を Claude 側で確認する（利用者には聞かない）:
   - 主体（`publisher`）が Q1 と合っている。個人なのに会社扱い、またはその逆に
     なっていない
   - `business.type` が業種に合う schema.org の型になっている（Q5）
   - JSON-LD の住所・電話・営業時間が、ページに表示している内容
     （`BusinessInfo` やアクセスページ）と一字一句一致している
   - `sameAs` が公式アカウントだけで、個人の私的なアカウントが混ざっていない
4. `pnpm check:jsonld --strict` が終了コード 0 になるまで直す（テンプレートの
   仮の値が残っていると失敗する。公開URLが未定の `example.com` は注記のみ）。

## 完了の条件

1. 次がすべて通る:
   `pnpm format && pnpm check && pnpm test && pnpm build && pnpm check:links && pnpm check:jsonld --strict`
2. `pnpm check:setup` が終了コード 0（未決定の項目を残した場合は、その一覧を
   利用者に伝えて完了扱いにしてよい）
3. 生成した OG 画像・アイコンを自分の目で確認した（`og-text` の日本語は
   マシンのフォントに依存するので、文字化けしていないか必ず見る）
4. 変更をコミットし、利用者に以下を報告する:
   - 作ったページの一覧と、未決定の項目
   - 検索エンジンに伝わる内容（`pnpm check:jsonld` の要約）
   - 公開手順（`README.md` の「Deploy」）: Cloudflare でリポジトリを接続する
     だけ（ビルド変数の設定は不要）
   - 公開後にできること: アクセス解析のトークン（`cloudflareBeaconToken`）と
     Search Console の認証コード（`seo.googleSiteVerification`）を教えて
     もらえれば `site.ts` に書き込む
   - 独自ドメインで HTTPS が安定したら `public/_headers` の HSTS を確認する

セットアップ完了後に内容を変えたいと言われたら、このフローの該当する質問だけを
聞き直して、同じ書き込み先を更新する。

| 目的             | コマンド                                                                  |

| 開発             | `pnpm dev`                                                                |
| 型チェック       | `pnpm check`                                                              |
| 単体テスト       | `pnpm test`                                                               |
| ビルド           | `pnpm build`                                                              |
| リンク検査       | `pnpm check:links`（`pnpm build` の後に実行）                             |
| JSON-LD 検査     | `pnpm check:jsonld`（`pnpm build` の後に実行）。`--strict` で仮の値も検出 |
| フォーマット     | `pnpm format`                                                             |
| セットアップ残り | `pnpm check:setup`（CIには入れない）                                      |
| 画像の再生成     | `pnpm images icons` / `og <画像>` / `og-text`                             |

CI と同じ検査をローカルで通すには:
`pnpm format:check && pnpm check && pnpm test && pnpm build && pnpm check:links && pnpm check:jsonld`

## 守るべきルール

1. **設定は `src/content/site.ts` に集約する。**
   サイト名・説明・ナビ・フッターリンク・問い合わせフォームURL・OG画像・
   robots・事業者情報はすべてここ。ページやコンポーネントに直書きしない。
   Header / Footer / SEO / JSON-LD / sitemap / webmanifest がここから読む。

2. **`.env` もビルド変数も使わない。**
   サイトのオリジンは `site.ts` の `url` → `astro.config.mjs` → `Astro.site`。
   コード内では常に `Astro.site` から読む。解析トークンや認証コードも
   `site.ts` に置く（どれも公開される値なので、コミットしてよい）。ファイルの
   編集だけで完結させ、スマホからでも設定を変えられる状態を保つため。
   **秘密の値（APIキー等）はこの方式で置かない** — 必要になったら Cloudflare
   のシークレットを使う別設計にする。

3. **URL形状は「末尾スラッシュなし」で1つだけ。**
   `trailingSlash: "never"` + `wrangler.jsonc` の `drop-trailing-slash`。
   `nav` の `href` も `/about` の形で書く（`/about/` と書かない）。

4. **`noindex` は `site.seo.noindexPaths` の1箇所だけで管理する。**
   meta robots（`Base.astro`）と sitemap 除外（`astro.config.mjs`）の両方が
   ここを見る。判定そのものは `src/lib/noindex.ts` の `isNoindexPath()` に
   集約してあるので、パスの一致規則を変えるならその関数を直す — 呼び出し側で
   条件を書き足すと、また2つの答えが生まれる。`lib/seo/` ではなく `lib/` 直下
   にあるのは、構造化データを丸ごと消しても noindex は残すため。

5. **構造化データは `src/lib/seo/jsonld.ts` に集約し、`@id` で相互参照する。**
   ページごとに単一の `@graph` を出力する。ノードを増やしたら
   `jsonld.test.ts` の参照解決テストが通ることを確認する。店舗情報
   （LocalBusiness）は `site.business` から自動で出るので、ページに直接
   JSON-LD を書かない。サイトの運営主体は `site.publisher` で決まる
   （`"Organization"` なら Organization ノード、`"Person"` なら Organization を
   出さず Person が publisher になる）。出力結果は `pnpm check:jsonld` で検査する。

6. **ランタイムJavaScriptは「動き」だけ。増やさない。**
   出しているJSは2つだけ: Astro の prefetch（約2.3kB）と
   `src/scripts/motion.ts`（出現演出とヘッダーの出し入れ、約1kB。GSAP 等の
   ライブラリは使わない）。加えて `Base.astro` の head に、描画前に合図の
   クラスを付ける数行の inline script がある。守ること:
   - **JS が無くても全部読める。** 要素を伏せるのは `<html>` に `.js-motion` が
     付いたときだけで、付けるのは head の inline script。JS 無効・動きを減らす
     設定（`prefers-reduced-motion`）では付かない。motion.ts が4秒以内に動かな
     ければ `.js-motion` を外して全部出す保険もある。
   - 動きは `data-*` 属性で指定する6種類だけ（`data-reveal` /
     `data-reveal-child` / `data-rule` / `data-img-reveal` / `data-pop` /
     `data-ink`）。見た目の定義は `global.css` の「動き」節。遅らせたいときは
     `style="--d:200ms"`。新しい種類が要るなら、まずこの6つで表せないか考える。
   - ループする動き（`anim-bob` / `anim-sway` / `anim-twinkle`）は装飾だけに。
   - オープニング（`Loader.astro`）は CSS だけで動いて自分で消える。訪問の
     2ページ目以降は出さない。不要なら `site.design.loader: false`。
   - UIの状態は CSS とネイティブ要素で（メニューは `<details>`）。問い合わせ
     フォームも自前で JS を書かず、外部フォームへのリンクにする。

7. **色は `src/styles/global.css` の `@theme` トークンだけを使う。ライト専用。**
   面: `bg` / `bg-2` / `surface` / `card` / `deep`、文字: `fg` / `muted` /
   `link` / `on-deep` / `on-deep-muted`、差し色: `accent` / `sun` / `bread` /
   `leaf`、罫: `border` / `border-soft`（`bg-bg`・`text-muted`・`border-border`
   …の形で使う）。生の hex や Tailwind の既定パレット（`text-gray-700` など）を
   書かない — 配色を差し替えたときに追従しなくなる。影の rgba だけは例外。
   **ダークモードは持たない**（`color-scheme: light`）。装飾イラストが明るい
   紙の地に置く墨線なので、暗い地では線が沈む。ブランド色は既存トークンの
   **値**を差し替えて表す。どうしても色を増やすなら `@theme` に足し、この
   リストにも追記する。
   - `accent`（赤）は 3.65:1 なので、大きな文字（24px 以上）と装飾だけ。
     小さな赤文字・赤いボタンの面は `link` を使う。
   - `sun`（黄）の上の文字は必ず `fg`。

8. **本文の見た目は `prose`（Tailwind Typography）に任せる。**
   各ページは `<article class="prose">` で組む。`--tw-prose-*` はトークンに
   束ねてあるので、prose 内で色を上書きしない。prose の外に出したい部品
   （カード・ボタン列など）は `not-prose` を付けてトークンで組む。

9. **横スクロールを発生させない。**
   ページ全体が横に動いた時点でモバイルとしては壊れている。防御は2層:
   長い単語やURLは `body { overflow-wrap: anywhere }`（`break-word` では
   min-content 幅が縮まず flex 配下で効かない）、埋め込みは
   `:where(img, svg, video, canvas, iframe, embed, object)` の
   `max-width: 100%`。幅の広い表（料金表など）は `overflow-x: auto` の
   ラッパ（`tabindex="0"` と `role="region"`、`aria-label` 付き）で包み、
   ページではなく表の中でスクロールさせる。`table { display: block }` は
   表のセマンティクスを壊すので使わない。

10. **最小タップ領域は `tap-target` ユーティリティが担保する。**
    「小さくなりうる」リンク・ボタン・`<summary>` に付ける。全デバイスで
    24×24px（WCAG 2.2 AA, SC 2.5.8）、`any-pointer: coarse` で44px。
    注意点が3つある:
    - 最小寸法を稼ぐ手段を `py-*` で自作しない（見た目のリズムのための
      padding は可）。寸法の単一の出所は `global.css` の `--tap-min`。
      数値を変えるならその変数を直す（ユーティリティ側に直接書かない）。
    - `block` / `flex` などの display ユーティリティと併用しない。カスタム
      ユーティリティは display グループより先に出力されるので負ける。
      すでに十分大きい要素（`FAQ.astro` の `<summary>` など）には付けない
      — 付けるとレイアウトが壊れる。
    - 文中のインラインリンクには付けない。SC 2.5.8 の除外対象であり、
      inline-flex の箱は行内に収まらない。

11. **ビューポート高は `dvh` を使う（`vh` ベースの `min-h-*` を書かない）。**
    モバイルのURLバー伸縮で `100vh` はずれる。
    なお `global.css` はこのファイルと `README.md` をクラス走査から除外して
    いる（`@source not`）。除外しないと、禁止クラス名を書いた行そのものが
    Tailwind にそのクラスを生成させてしまう。

12. **書体は `astro.config.mjs` の `fonts`（Astro Fonts API）の4つだけ。**
    本文 `font-sans`（Zen Kaku Gothic Antique）、大見出し `font-head`（Kaisei
    Decol）、手書き風 `font-hand`（Yomogi）、欧文の添え字 `font-en`（Josefin
    Sans）。ビルド時に Google Fonts から取得して自己ホストする（閲覧者は外部に
    接続しない。CSP は `font-src 'self'` のまま）。和文はサブセット分割される
    ので preload しない。書体を替えるときは `fonts` の `name` を替えるだけで、
    `--font-raw-*` と `global.css` の `--font-*` の対応はそのまま。どれも SIL
    OFL 1.1（`LICENSE-FONTS.md`）。5つ目を足さない — 和文1書体で数百ファイル増える。

13. **装飾イラストは `src/assets/images/deco/`、絶対配置ではみ出させる。**
    はみ出す装飾を抱える節には `deco-clip`（`overflow-x: clip`）を付ける。
    装飾は `alt=""`、多くはスマホで隠す（`hidden lg:block` 等）。写真・ロゴは
    `<Image>`（astro:assets）で出し、`public/` に置かない。

## テストの方針

- 対象は「壊れても画面上は正常に見えるもの」= JSON-LD の参照構造と
  noindex 判定。見た目のスナップショットは取らない。
- 外部の契約に依存するテストは、その契約を実際に動かして検証する（モックした
  入力を読み返すだけのテストは書かない）。
- `src/**/*.test.ts` を Vitest が拾う（`vitest.config.ts` は `getViteConfig` を
  使うのでテストからも `astro:*` を解決できる）。
- `scripts/check-jsonld.mjs` は `dist/` の全ページの JSON-LD を検査する
  （1ページ1つの `@graph`、`@id` の重複なし、参照がすべて解決する）。
- `scripts/check-links.mjs` は `dist/` の内部リンクのみ検査する。外部リンクは
  意図的に叩かない（CIが外部要因で落ちるため）。

## やらないこと

- UIキット・CSSフレームワークのランタイム・クライアントサイドルーター・
  アニメーションライブラリ（GSAP 等）の導入
- `tailwind.config.js` の追加（Tailwind 4 は CSS 内の `@theme` で設定する）
- 見た目だけのための抽象化レイヤー
- ブログ・お知らせなどの記事機能の再導入（必要になったら別途設計する）
